# apps/api

Composition root, auth, versioned HTTP, SSE (see [BankOps_05_Backend_Design.md](../../documents/BankOps_05_Backend_Design.md)).

**Framework/version:** ASP.NET Core, .NET 10 (pinned 2026-09-24). Scaffolded with `dotnet new webapi --use-controllers` — controller-based, OpenAPI enabled by default. Template's sample `WeatherForecastController`/`WeatherForecast.cs` removed.

**Auth (2026-09-24):** JWT bearer auth wired up against [infra/DevIdentityProvider](../../infra/DevIdentityProvider/README.md) (dev-only OIDC issuer — not D-01's real IdP). `MapInboundClaims = false` is required in `Program.cs` — without it, role claims get silently rewritten to legacy WS-Identity URIs and every `[Authorize(Roles = ...)]` check fails closed with a 403 that looks like a config problem, not a bug. `Controllers/AuthProbeController.cs` is a temporary object-level RBAC test endpoint (401/403/200 cases verified) — delete it once `modules/identity` has real endpoints.

**Cross-cutting foundations (2026-09-24):**
- **Error format** — `GlobalExceptionHandler.cs` catches unhandled exceptions and returns RFC-7807 ProblemDetails: `code`, safe user text (never the raw exception message/stack trace), `correlationId`, `retryGuidance`. Verified: `GET /api/v1/diagprobe/boom` (temporary, delete later) returns 500 with all four fields.
- **Correlation IDs / telemetry** — `CorrelationIdMiddleware.cs` reuses the W3C trace ID that ASP.NET Core's `Activity` already generates per request (one ID scheme, not two) and echoes it as `X-Correlation-Id`. OpenTelemetry wired up for tracing + structured logs, console exporter only — D-04 (real telemetry backend) is still an open Phase 0 decision, swapping exporters later is a one-line change here.
- **Feature flags** — `FeatureFlags/` — `IFeatureFlagService` (config-backed for now, `platform.app_settings` via `modules/settings` later, same interface). `[FeatureGate("name")]` action filter returns **404, not 403**, when a flag is off — a disabled feature's routes should look like they don't exist, not leak that they exist behind a permission. Verified: off by default → 404 even with a valid admin token (proves "direct URL cannot bypass flag" per FR-004); on + right environment + right role → 200; on + wrong role → still 404.
- **Secrets** — `Secrets/ISecretResolver.cs`, backed by `dotnet user-secrets` locally (never appsettings.json — a secret can't accidentally get committed). Swapping to the bank's real approved vault (NFR-SEC-04) later is a new `ISecretResolver` implementation, no call-site changes. Verified: resolves the dev DB connection string, confirmed only its length was logged, never the value.

**First real modules wired in (2026-09-24):** `modules/settings` and `modules/audit` — apps/api now opens a real `NpgsqlDataSource` at startup (connection string read straight from config, not through `ISecretResolver`, since the DI container that would resolve it doesn't exist yet at that point in `Program.cs`). `HttpContextCurrentPrincipal.cs` implements `contracts/ICurrentPrincipal` — the composition root's job per the backend design, since it's the only layer that knows about `HttpContext`. Full create → conflict → update → audit-trail → RBAC sequence verified end-to-end and automated in `tests/BankOps.Api.IntegrationTests/SettingsAndAuditTests.cs`.

A real gotcha hit here: `AddWithValue` can't infer a Postgres parameter's type from a bare `DBNull` (the common "no expected version yet" case), causing `42P08: could not determine data type of parameter` — fixed with an explicit `NpgsqlDbType` in `modules/settings/Infrastructure/SettingsRepository.cs`. Also: once `apps/api` required a real DB connection at startup, the `api-auth-tests` CI job (which never touched DB-backed endpoints) would have broken silently in CI — it only "worked" locally because of leftover `dotnet user-secrets` on this dev machine. Fixed by making `AuthTests` set its own placeholder connection string rather than depending on execution order or local machine state; verified by temporarily hiding local user-secrets and re-running.

The API never waits on a live SolarWinds/T24/Commvault call to render a response — it reads a consistent materialized view/snapshot that the worker maintains. Every request authenticates, then checks operation permission + resource scope + feature availability + environment, at the API boundary and again inside the application command before commit.
